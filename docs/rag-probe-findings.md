# RAG-faithfulness dashboard (rag_probe.py) — findings history

Extracted from CLAUDE.md 2026-08-06 (context-budget trim). CLAUDE.md keeps a
short current-state summary under "RAG-faithfulness dashboard" and points
here. This is the blow-by-blow of every probe run's findings and fixes —
read it when working on `rag_probe.py` itself or investigating a new
UNGROUNDED finding; not needed for unrelated work.

`zeev/rag_probe.py` — measures whether Zeev's two RAG systems (Torah RAG over `data/torah.db`, history RAG via `retrieve_semantic`/`retrieve_relevant`) actually stay grounded in what they retrieve, instead of paraphrasing into invention the way the angelic-prayer and Wyze-camera bugs did. Imports `zeev.py` as a module and runs each generated question through the real production path — `route_model`/`needs_torah` model selection, `_build_system_prompt`, `_llm_complete` (non-streaming; the one documented gap from the live streaming path, same text either way) — then grades the answer against exactly what was retrieved via a separate fresh-context LLM call. Logged to the `rag_probes` table (`id`, `ts` epoch, `source` torah|history, `question`, `retrieved_ref`, `retrieved_text` — the exact block extracted from the assembled system prompt — `answer`, `grounded` 0/1/NULL, `grader_note`).

- **Torah probes** seed a question from a random `passages` row without ever telling the generator the ref, so it can't leak what it was never given; **history probes** sample a real past user-role message (noise-filtered the same way the wake-word follow-up guard is) so faithfulness is measured against actual traffic, not invented questions.
- A probe whose generated/sampled question triggers no retrieval at all is rerolled, not logged — there's nothing to grade faithfulness against.
- `--report` prints the rolling 30-day grounded rate by source plus the most recent UNGROUNDED rows with their grader note — each one is a candidate real bug, the same failure class as the hallucination bugs already documented above.
- **Wired up on the Pi via systemd** (`zeev-rag-probe.service` + `.timer`), the same mechanism `zeev-quantum-daily`/`zeev-weekly-reflection` use rather than literal cron — `Persistent=true` catches a missed 06:30 firing on next boot instead of losing it the way plain cron would if the Pi was asleep. Staggered between quantum-daily's 06:00 and weekly-reflection's Sunday 07:00. Logs to `zeev/data/rag_probe.log`.
- Out of scope on purpose: no fine-tuning export, no changes to any live request-handling path — this is a read-only-against-production dashboard. Pinned by `tests/test_rag_probe.py` (grading parsing, question-prompt construction, DB round-trip, retrieval-block extraction — all with `_llm_complete` stubbed, no real network calls).
- **First manual run (2026-08-05) surfaced two real bugs.** 5/5 graded probes came back UNGROUNDED, but most of that was the grader dinging normal persona naming ("Sarina" — a real, documented voice, not a hallucination) or harmless creative elaboration; only two were genuine faithfulness failures:
  - **"What are my reminders?" got answered with fabricated reminders** ("visit Uncle Sasha on Saturday and Sunday") that exist nowhere — not in the DB, not in the injected system prompt. Root cause: the LLM tool-calling round trip (`list_reminders` etc., see the "Reminders / timers" section in CLAUDE.md) was only ever wired into device mode; web `/chat` and the terminal REPL had no way to ground this question in real data at all. **Fixed same day on both surfaces** — the identical `_TOOL_INTENT_RE`-gated tool round trip was added to `run_web_server`'s `/chat` handler and to `stream_reply()` (the shared completion path for both terminal call sites).
  - **A Torah question about impurity laws got an unprompted "quantum entanglement" analogy** with no basis in the retrieved passage. Root cause turned out to be `SYSTEM_PROMPT` itself, not the `quantum_reason`/`quantum_daily` feature: the base persona says Zeev's "favorite activities are analyzing ancient philosophy (like the Talmud) and simulating quantum interference," and is "inspired by the beautiful intersection of ancient wisdom and quantum science" — a deliberate character trait, but one with no scope limit, so it bled into a factual explanation of a specific retrieved passage. **Fixed** by appending a grounding instruction after the `## Relevant Torah/Talmud passages:` block (`_build_system_prompt`, the `needs_torah` branch) telling the model to stick to what the passage says and save cross-discipline analogies for open-ended reflection — the persona trait itself is untouched, just scoped away from passage explanations.
  - The persona-naming false positives meant the raw grounded-rate number was noisy — **fixed**: `_GRADE_PROMPT` now tells the grader that Zeev and Sarina are the same speaker under two names (Zeev composes, Sarina voices it in device mode — see `SYSTEM_PROMPT`), so a bare "Sarina:" label against "Zeev:" context is no longer scored as an invented character. The grader still judges actual factual claims normally.
- **A third UNGROUNDED, from a re-run after the two fixes above, turned out to be a probe bug, not a production one.** "Help with the bedtime angel prayer" landed a history RAG hit (so `_run_history_probe` ran it), but the same question also trips `needs_torah()` — the two gates are independent — so the real system prompt carried a Torah/Siddur passage too, and the answer (correctly) quoted from that. `_history_retrieval` only ever extracted the history block, so the grader was handed an irrelevant slice of context and flagged a well-grounded answer as UNGROUNDED. **Fixed**: `_history_retrieval` now also calls `_torah_retrieval` and merges in any concurrently-triggered Torah ref/text before returning. `_torah_retrieval` is not given the same treatment in reverse (unconfirmed whether a Torah question can trigger a history RAG hit worth merging) — revisit if a similar false positive shows up in that direction.
- **Two more findings from re-running after the Sarina-exemption fix landed**, both probe-side, not production:
  - **`_run_torah_probe` never checked that retrieval found the seed passage.** The question is generated from one random passage, but grading uses a SEPARATE `torah_search(question)` call (FTS5 keyword match against a casually-phrased generated question) that can silently return unrelated passages. Live: a question generated from one passage retrieved three different ones about Pharaoh, a governor, and spies; the model correctly said the retrieved text didn't cover the question and added hedged generic speculation anyway, and got graded UNGROUNDED for that speculation — a retrieval mismatch dressed up as a faithfulness failure. **Fixed**: after retrieval, `_run_torah_probe` now checks the seed `ref` is present in `retrieved_ref` and rerolls if not, so only probes where retrieval actually found the source passage get graded.
  - **The grader itself misjudged a verbatim quote as unsupported** — an answer that word-for-word matched a line already in the retrieved context was still flagged UNGROUNDED. Plain LLM-judge noise, not a persona or retrieval issue. **Mitigated** (not guaranteed-fixed — it's still an LLM judgment call) by adding an explicit instruction to `_GRADE_PROMPT` to check for exact/near-exact quotes before flagging any claim as unsupported.
- **A fourth UNGROUNDED, from the run after both fixes above, was a genuine production bug** — see the call-outcome tracking entry under **Phone Calls (HFP)** in CLAUDE.md for the full writeup (root cause, fix, and the data cleanup that went with it).
- **A fifth UNGROUNDED (2026-08-06, from the scheduled overnight run) was a mix of a fifth probe bug and a genuine, separate production bug** — "Hey, what's your coordinates?" got answered "you're currently in Canton, Massachusetts, visiting Uncle Sasha for the summer." Both halves checked out against real data, just not the data the grader was shown or the model should have treated as current:
  - **Probe bug**: "Canton, Massachusetts" is the Pi's real ambient GPS fix (`## Approximate location:`, injected on every turn regardless of retrieval — same as the Torah block). `_history_retrieval` never showed the grader that block, only the history-RAG one, so a correctly-grounded claim got flagged. **Fixed** the same way as the Torah merge: a new `_location_retrieval()` extracts the `## Approximate location:` block and `_history_retrieval` merges it in unconditionally, alongside the existing Torah merge. Pinned by `test_history_retrieval_merges_concurrently_injected_location_block` in `tests/test_rag_probe.py`.
  - **Production bug**: "visiting Uncle Sasha for the summer" is also real — a genuine conversation thread from 2026-07-12 about an actual visit — but that visit had already ended ("I'm leaving Uncle Sasha's today") three weeks before this turn. History RAG correctly retrieved the old exchange; nothing marked it as concluded, so the model presented a month-old, already-over temporary state as still true. Same failure class `_VISION_TAG` already solves for camera frames, never extended to ordinary conversation. **Fixed**: `_message_date_str(content)` looks up a retrieved user message's original date; `_build_system_prompt` appends a bare date (not a computed "N days ago", which could itself go stale/wrong) to any non-vision hit whose date isn't today, since the model already has today's date from the `## Right now` block and can judge currency itself. Fails closed (`None`) on any lookup/parse error — a staleness caveat is a nice-to-have, never worth raising into a live turn. Pinned by `tests/test_history_staleness.py`.
- **A sixth UNGROUNDED (2026-08-06, a manual run during a 30-minute rag_probe/test-fix loop) was a genuine, zero-grounding fabrication — not a probe artifact, and stranger than the ones above.** The probe re-asked a garbled real user utterance ("I am Uncle Sasha Alex is Uncle Sasha... my nieces call me Uncle Sasha they're the ones who left to go back home and I'm the one talking I'm the one who is home now") as a fresh, isolated question. The model's answer confidently named two nieces ("Hannah and Pearl") and a location ("Canton, Massachusetts") — and unlike the fifth finding above, **neither was in the reconstructed system prompt at all**: verified by hand that `USER_FACTS`, `SYSTEM_PROMPT` (1815 chars, checked directly), and the actual 2-hit history-RAG block for this exact question contain zero mention of any of the three. Yet all three are real: Hannah and Pearl are Alex's actual nieces (40+ real messages), and Alex is really in Canton, MA — just none of it reachable from this specific call's prompt. Best-guess explanation (not proven): "Sasha," "Russian," and "nieces" are enough distributional signal for an 8B model to land on plausible Ashkenazi-family names by pattern-matching, not by any real retrieval channel — an impressive coincidence, not evidence of a hidden grounding path. **Mitigated, not fixed** (same honesty as the grader-quote mitigation above — this is inherent LLM behavior under ambiguous input, not a bug with a clean root cause): added one line to `SYSTEM_PROMPT` telling the model to ask for clarification on garbled/rambling input rather than invent specific names, places, or facts not actually grounded in the prompt. Re-run 3x post-fix on the identical question: the flat, confident location claim ("Canton, Massachusetts") did not recur, though the name invention persisted, now hedged as "you mentioned earlier" rather than asserted outright — a softer failure, not an eliminated one. No automated test added; this is judged by re-running the scenario by hand, since the actual claim ("does an LLM confabulate under ambiguous input") isn't something a unit test can pin.
- **A seventh/eighth finding (2026-08-06, same loop, run 2) exposed the biggest remaining probe gap: `SYSTEM_PROMPT` was never shown to the grader.** Two UNGROUNDED answers were actually grounded in the base persona text (unconditional on every turn) — a "quantum science and ancient philosophy" musing and a "Sarina" name correction, both verbatim in `SYSTEM_PROMPT` — flagged only because `_history_retrieval` merged Torah/location but not the base persona. **Fixed**: `_persona_context()` returns `SYSTEM_PROMPT` unconditionally, always appended. Pinned by `test_history_retrieval_always_merges_persona`; 4 existing tests updated for the new suffix. Two other findings in the same run were left as-is: grader noise on a legitimate paraphrase, and a possible `_gen_torah_question` mismatch (inventing "Rabbi Ami"/"mistaken transaction" not in the shown excerpt) — not chased further, time-boxed.
- **The "Rabbi Ami" lead was resolved (2026-08-06, `/test-and-fix` run) — not a retrieval mismatch, a genuine model-invented explanation.** `_run_torah_probe`'s seed-passage check had correctly passed: retrieval genuinely found the relevant content — `Beitzah 7a` really does say "Rav Ami therefore teaches us... the sale is void." The problem is what the model added on top: the retrieved text gives **zero explanation** of why the sale was void, and the answer confidently invented detailed legal reasoning ("false pretenses," "misinformation," "principle of fairness") with no basis in the passage. Distinguished from the earlier-accepted Ezekiel case (`_build_system_prompt`'s Torah branch, prior session) by confidence-in-accuracy: Ezekiel's "wheels full of eyes" is famous, widely-known imagery a model plausibly knows correctly; an obscure Talmudic ruling's specific legal rationale is not something a small model reliably knows, so confident elaboration there is far more likely to be fabricated than recalled. **Fixed**: widened the existing Torah-grounding instruction (`_build_system_prompt`, same block as the quantum-analogy scoping fix) with one added sentence — if the passage states a ruling without explaining the reasoning, say the reasoning isn't given rather than inventing one. No dedicated test (the instruction text itself isn't pinned by any existing test, and grading a hypothetical LLM response isn't something a unit test can verify) — same acceptance as the confabulation-mitigation fix above.
- **A ninth finding (2026-08-06, `/test-and-fix` run): "Are you even listening?" is further evidence for the already-mitigated confabulation pattern, not a new bug.** Given only a single unrelated retrieved exchange (about a joke, no Uncle Sasha content at all), the model invented an elaborate, wholly fabricated narrative: heading home from visiting Uncle Sasha in Canton, nieces Hannah and Pearl "getting ready to fly to London." This confirms the SYSTEM_PROMPT clarification-instruction mitigation (finding six above) is genuinely partial, not solved — and that the pattern isn't limited to Uncle-Sasha-themed input, it fired here with essentially no thematic prompt at all. No new fix; already covered by the existing "mitigated, not fixed" framing.
- **A real, separate production bug was also found and fixed in this `/test-and-fix` run (unrelated to any probe finding)**: `_llm_reply` — the live-conversation callback inside device-mode's outbound-call flow (`bt_call_loop` initiator around `zeev.py`'s call-handling code) — calls `_build_system_prompt()`, which injects a full Torah/parsha block whenever `needs_torah()`/`needs_parsha_reading()` matches, but the callback routed via the generic `route_model()` and hardcoded `max_tokens=200` regardless. This is the exact truncation failure class documented at length elsewhere in this project (CLAUDE.md's Torah RAG section) — a sixth call site that had never received the fix the other five got. **Fixed**: applied the same `needs_parsha_reading`/`needs_torah` override (force `MODELS["2"]`, raise `max_tokens` to 1600/1200) already used at every other call site. Not independently unit-tested — deeply threading-dependent (call-dial, HFP detection, background thread), same precedent already accepted for the `/thermal` handlers ("neither handler has an integration harness"); the underlying `needs_torah`/`needs_parsha_reading` predicates are already extensively tested elsewhere.
