# Whisplay HAT device mode — full history

Extracted from CLAUDE.md 2026-08-06 (context-budget trim). CLAUDE.md keeps a
condensed summary of the highest-impact gotchas under "Whisplay HAT device
mode" and points here for the full incident history. Read this when actually
working on device-mode audio/wake/streaming/display code.

`python3 zeev/zeev.py --device`

- **TTS priority**: Groq Orpheus → gTTS + mpg123 (he/es/ru) → Piper (en, one-shot for BT, persistent for speaker) → espeak-ng
- **Streaming replies**: `_stream_speak()` flushes complete sentences to TTS as the LLM generates them, so time-to-first-audio is one sentence rather than one completion. Batching is greedy to the last terminator with a 45-char floor. Tokens are drained by a producer thread — `_speak_device` blocks for the duration of the audio, and the 1600-token Torah path would otherwise leave the HTTP response unread long enough to be dropped. `STREAM_TTS=0` reverts to the buffered path. The 429→8B and 413→trim chains are unaffected (`status_code` is available before the body is read). Chunking rule pinned by `tests/test_stream_chunking.py`; the tail rule is subtle — a dangling fragment is dropped, but a reply with *no* terminator is still spoken, distinguished by whether anything was spoken yet.
- **Interrupting speech (three separate bugs, all fixed together)**: the button did nothing once the Go daemon owned playback. `_interrupt_tts` only killed `_tts_p1`/`_tts_p2`, which are `None` on the daemon path.
  1. Daemon `stop` only stops **music**. Speech needed its own `speak_stop` command (`audio.CancelSpeech()` + `audio.StopPlayback()`).
  2. Killing `aplay` is not enough: `speakPiper` feeds one `APlayPipe` from a loop that **blocks on `<-results[i]`** waiting for later sentences to synthesize, so a cancel mid-synthesis had nothing to kill and the loop kept waiting. Hence the `context` scope (`BeginSpeech`/`CancelSpeech`) and the `select` on `speechCtx.Done()`.
  3. Cancelling made `speakPiper` return an error, and the handler's fallback then **re-spoke the whole reply through espeak-ng** — which looked exactly like the cancel not working. `audio.ErrSpeechCancelled` is now treated as success, never as a synthesis failure.
  - Python side: `audio_client.speak_stop()` opens its **own short-lived socket**. Every other call serializes behind `self._lock` on one socket, so a stop sent during `speak_sync` would queue behind the very speech it was cancelling.
  - `_on_press` now also interrupts during `thinking`, not just `speaking` — with streaming, state stays `thinking` until the first sentence flushes.
- **Volume percent is linear in dB, NOT in the raw register.** WM8960 `Speaker` is 0–127 in **1 dB steps** — raw 121 = 0 dB, raw 127 = +6 dB, and anything under ~48 is below −73 dB, i.e. off. The original `pct/100*127` therefore made the slider linear in *decibels*: ~12.7 dB per 10% (more than doubling loudness per notch) with the bottom third of the range inaudible. Measured 2026-08-01: **"40%" was −70 dB (silent, reported as "almost muted") and "90%" was −7 dB (reported as merely "normal")** — which is exactly how it read to a person. `_pct_to_raw()` now maps 1% → −40 dB and 100% → +6 dB, so **70% ≈ −8 dB (comfortable) and 90% ≈ +1 dB (loud)**. 0% is true mute.
  - **The Go daemon has its own copy (`pctToRaw` in `internal/audio/alsa.go`) and the two MUST agree** — the Python path runs whenever the daemon is down, so divergent curves make the same percentage sound different depending on which set it. Pinned by identical tables in `tests/test_volume_curve.py` and `alsa_test.go`.
  - This card has **no `Master` control**, so the `amixer sset Master` attempt always fails and the Speaker fallback is the real path.
  - `_STARTUP_VOLUME` default moved **90 → 70** with the remap so the device did not silently get louder: both are ≈ −7/−8 dB.
- **Speaker volume**: `_STARTUP_VOLUME` (default **70%**, ≈ −8 dB) via amixer at startup; override with `ZEEV_VOLUME`. The speaker is inches from the mic with no echo cancellation, so louder settings feed more of Zeev's own voice into the wake detector — turn this down first if false wakes reappear. `_VOLUME` is initialized from the same constant so `/volume` doesn't report a stale value. BT headphone volume: raw 50/127 (~39%).
- **STT**: Groq Whisper `whisper-large-v3-turbo`.
- **`_greeting_done` event**: gates the wake listener so it can't self-trigger on the greeting audio through the mic.
- **Wake word ("Miss Minutes")**: `_wake_listener()` picks one of two front-ends, both feeding the shared `_wake_dispatch()` (session claim → beep → dispatch or record follow-up), so the paths can't drift on state handling.
  - **openWakeWord (preferred)**: one continuous 16kHz raw `arecord` stream, scored on-device per 1280-sample (80ms) frame. Enable with `OWW_MODEL_PATH` in `.env`; `OWW_THRESHOLD` (0.5) and `OWW_COOLDOWN` (2.0s) tune it. Install `onnxruntime` + `openwakeword`.
    - **Measured on the Pi Zero 2W**: RTF 0.68, **~70% of one core** (of four), **166 MB steady RSS**, 4.8s model load (plus ~14s to import onnxruntime, which is not counted in the logged time). Coexists with the rest of zeev-device at ~257 MB of 463. Not cheap — it only runs in `idle`/`ready` and releases the mic and the core the moment a turn starts.
    - **Startup order matters more than the load time.** The load measured 4.7s settled and **3171s at boot** — the wake word was deaf for the first 53 minutes after a reboot. Nothing is wrong with the load; every startup task wants cold pages off the SD card at once on a 463 MB board and they thrash. The mic is the primary input, so it goes first: the model load runs *ahead* of `_greeting_done.wait()` (playback doesn't need it; the wait guards the mic, which opens after), and the `shapes_test`/Piper prewarms park on `_wake_model_ready` until it completes. That event is set in a `finally`, so a bad model path releases them instead of stranding them. **Cold boot to armed is now 44s** — ~7s of process startup, ~14s importing onnxruntime, ~7s of model load (the only part the `in 6.6s` figure covers), the rest contention. The ready line logs `avail`/`swap` (`_mem_snapshot()`) because a slow load is the symptom of thrash and there is otherwise no way to tell the two apart after the fact.
    - **Energy gate** (`OWW_ENERGY_GATE`, on by default): skips `model.predict()` on frames below a rolling noise floor (median of ~6s × `OWW_ENERGY_MULT` 1.8, floored at `OWW_ENERGY_MIN`). **The non-obvious part**: openWakeWord scores a *rolling* buffer, so naively skipping frames feeds it discontinuous audio — the wake phrase stitched onto whatever preceded the silence. On speech onset it therefore calls `model.reset()` and replays an `OWW_PREROLL` (~0.5s) pre-roll, then holds inference on for `OWW_HOLD_FRAMES` (~2s) so a pause mid-phrase doesn't gate out the rest.
      - Offline against real speech: peak score **0.998 gated vs 0.999 ungated** on 20% of frames, 5.6× less CPU — detection is unaffected.
      - Live on the device: **66.6 °C → ~60 °C**, load 1.06 → ~0.75. The real room only skips ~35–40% of frames (vs 80% offline) because ambient noise is well above synthetic room tone; the gate adapts upward, logging `[wake] energy gate: scored N/M`. Raise `OWW_ENERGY_MULT` to skip more, at the cost of quiet wake words. `OWW_ENERGY_GATE=0` disables it.
      - **`OWW_ENERGY_MULT=2.5` is set on the Pi** (2026-07-30; `.env` only, not in git). The board had drifted to **68.8 °C / 91.9% CPU / load 1.00** — well above the figures above — and 2.5 brought it to **65.8 °C / 60.4% / load 0.71**, frames scored 61–63% → 31–38%. Measured over ~2 min each side with `/proc/<pid>/stat` deltas; **`ps -o pcpu` is a lifetime average and lags across a restart**, so it reads the old value for minutes and is useless for this comparison.
      - **Sensitivity at 2.5 is only partly validated**: one live wake at normal volume scored **0.80** against a 0.5 threshold, so it cleared with margin. Quiet/distant wakes and a wake over TV noise are untested, and that is precisely where a higher gate bites — the gate is `median × MULT`, so it climbs with the room, and it was observed at **13387** during a loud stretch (vs ~3200 quiet). If wakes start getting missed, drop it back to 2.2 before suspecting anything else.
    - **Thermal context**: idle Pi with zeev-device stopped sits at **58 °C**; running it is ~59–63 °C, and 65.8–68.8 °C at the hotter wake-gate settings. Throttling starts at 80 °C and the sticky `vcgencmd get_throttled` register has stayed `0x0` — it has never actually throttled.
      - **Every one of those figures is measured inside a custom 3D-printed enclosure**, not in free air — translucent natural filament, LCD window, back panel on 4 corner screws. It **is vented** (a ~24-hole grid plus a recessed 3-hole port on the back, and the base port cutouts pass air), so it is not a sealed shell; but a bare Zero 2W in open air is ~40–45 °C, so the gap is the HAT/PiSugar stack *plus* the case. Note the base cutouts face whatever the device rests on and can be blocked by it.
      - **Material is PLA** — the Etsy listing's materials field reads "Biodegradable Non Toxic Plastic" (PETG is not biodegradable). The configuration is the seller's official `PS23_1200/Whisplay` option; its 8× M2×3 countersunk screws are the ones visible at the corners.
      - **PLA's ~60–65 °C glass transition is NOT a problem here, despite the SoC reading 59–63 °C.** Those two numbers are not comparable: `vcgencmd measure_temp` reports the **die**, while the plastic is spaced away from it and runs far cooler (a case merely hot to the touch is ~40–45 °C). Don't repeat the mistake of comparing a die temperature against a material's Tg.
      - Mic and speaker have **purpose-cut ports** rather than solid plastic over them, so attenuation is less than a closed box would give — but wake/whisper RMS figures were still captured through this build and are not comparable to published openWakeWord numbers.
      - Do **not** fit a fan: it sits centimetres from the mic, raises the noise floor the wake gate tracks, and degrades STT. Inside a closed case the remaining levers are ventilation slots, a heatsink onto the SoC, or accepting the current ~18 °C of headroom.
    - **pip resolves 0.4.0, not 0.6.x, on py3.13/aarch64** — newer releases depend on `tflite-runtime`, which has no wheel there. 0.4.0 is onnx-only and bundles its models (`resources/models/*.onnx`, incl. `hey_jarvis_v0.1.onnx`). Don't blind-upgrade it. Note the API differs from current docs: `Model(wakeword_model_paths=[...])`, and there is no `download_models`.
    - **`vad_threshold` is not a saving** — in 0.4.0 Silero runs *in addition to* the main model, measured 75.6% vs 65.6% of a core. Left off deliberately.
    - **`OWW_THRESHOLDS`** (`stem:0.80,stem:0.55`) overrides the global `OWW_THRESHOLD` per model; unlisted stems keep the global. Thresholding happens **per model before the max is taken** (`oww_best`), or a model with a raised bar would mask a quieter one that legitimately fired. Measured live 2026-07-29 over the model's first 3h35m of household conversation, though: `sarina`'s real wakes spanned 0.58–0.98 and its false wakes 0.51–0.73 — **overlapping, so no threshold separates them**. 5 false wakes in 3h35m (~1.4 fp/hr, 7× upstream's 0.2 target) on fluent speech is a phrase-length problem; the fix is retraining as "Hey Sarina", not the knob. `zeev.onnx` in the same window: **zero real wakes, one false one** — a net negative as trained. **Both phrases were retrained as "Hey Sarina" / "Hey Ze'ev"** (4 syllables) and **installed 2026-07-30**: `OWW_MODEL_PATH=…/hey_zeev.onnx,…/hey_sarina.onnx`, `OWW_VOICE_MAP=hey_zeev:daniel,hey_sarina:sarina` — both lines move together because `MODEL_NAME` becomes the prediction key. Ready line confirms the keys: `hey_zeev, hey_sarina in 7.8s`. The old `zeev.onnx`/`sarina.onnx` stay in `~/oww/` so rollback is one `.env` edit. **Whether the prefix actually helped is not yet measured** — count false wakes *per model* over a few hours; if both fire on the same conversational audio the shared "Hey" onset bought syllables without separation, and the next lever is sample count or a distinctive consonant onset, not another prefix. See `docs/wake-word-training.md`.
    - **`zeev/wake_enroll.py`** (2026-08-04, `docs/research-directions.md` #3): a lighter alternative to retraining when the phrase is fine but the household's actual voice/mic scores lower than the stock model expects. Records a handful of enrollment clips (`arecord`), scores each against the loaded model(s) via `oww_score_pcm` (peaks a rolling `model.predict()` buffer per clip, resetting first), and suggests a per-stem `OWW_THRESHOLDS` value via `enroll_suggest_threshold` — a margin below the *weakest* clip, since that one is the binding constraint. **Can only lower a threshold, never raise one**: a few positive clips prove genuine wakes score at least this high, but say nothing about false positives on other audio (that needs negative examples — see `wake_harvest.py` below, not this). Prints by default; `--apply` merges into `.env`'s `OWW_THRESHOLDS` line, never silently. Pi-only in practice (needs a real mic and `openwakeword`) — hasn't been run live yet, only the scoring/suggestion/merge logic is tested (`tests/test_wake_enrollment.py`).
    - **`zeev/wake_harvest.py`** (2026-08-04, `docs/research-directions.md` #4): closes the loop the other direction — turns *false* wakes already sitting in the journal into hard negatives for the next retraining round, instead of `wake_enroll.py`'s genuine-wake threshold tuning. Parses `journalctl -u zeev-device` for `[wake] ... trigger` lines and pairs each with the transcript that followed (`_wake_dispatch` prints nothing of its own in between, so they're adjacent in the normal case; tolerates up to 30 intervening lines from other threads before giving up and dropping the trigger, counted rather than silently vanishing). The noise-transcript branch parses the log's `!r` (Python repr) properly via `ast.literal_eval` rather than a naive quote-strip, which breaks on a transcript containing an apostrophe. A transcript already saved, or already seen earlier in the same run, is skipped without asking — the same false wake recurs constantly (a TV ad plays daily), and re-asking trains the reviewer to rubber-stamp "y". Interactive: walks through each candidate, saves the ones marked false to a JSON array droppable into `custom_negative_strings` in the training notebook. Tested end to end except the actual journalctl call and stdin (`tests/test_wake_harvest.py`).
    - **Custom phrases**: train a `.onnx` with openWakeWord's automatic training notebook (free, ~75–90 min on a Colab T4). Verified that a model trained on the modern pipeline loads and runs under the 0.4.0 runtime, so trained models drop straight in. See `docs/wake-word-training.md`. **The Pi currently loads one model** (`hey_jarvis` → sarina): the stock `alexa` model was dropped because television advertising sets it off. `.env` is not in git, so that config lives only on the Pi.
    - **`model.reset()` is mandatory, not hygiene (caused an endless loop live)**: `predict()` scores a *rolling* buffer of embeddings. Killing `arecord` when a turn starts and restarting it afterwards does **not** clear that buffer, so the previous turn's wake phrase is still inside it and scores again on the first fresh frame. Symptom: every reply's `[+Ns] Done` followed in the same second by `trigger (score 1.00)` — **an identical score every time means stale buffer, not a real detection**. Zeev answered its own noise forever. `reset()` now runs on trigger and again before re-arming.
    - **`OWW_SETTLE` (1.5s)**: quiet period after a turn before the mic re-arms. The speaker is inches from the mic with no echo cancellation, and accepting `ready` re-arms instantly, so the tail of Zeev's own reply retriggers the wake word. Related: startup volume was dropped to 65% partly to weaken this feedback path.
    - **Follow-up transcripts are noise-guarded** with `re.search(r'\w{2,}')`, the same check `bt_call_loop` uses (`zeev.py:~2880`). A spurious wake records room noise and Whisper returns confident nonsense (`"A A"`, `"Ache, a full-tongue, a full-tongue"`) which otherwise becomes a real LLM turn and keeps a loop fed.
      - **That was only half of `bt_call_loop`'s guard, for months, while the comment claimed parity.** Whisper does not return an empty string for silence — it returns a confident closing line from its training data, and `\w{2,}` cannot catch those because they are perfectly good words. Live 2026-08-02 15:13 a false wake transcribed as **"Thank you."**, Zeev replied "You're welcome, Alex.", and **both halves were embedded** — a fabricated exchange that semantic recall can surface later as fact. `_is_whisper_hallucination()` is now shared by both paths, matched **whole, never as a substring**, so "thank you for the reminder about therapy" still gets through.
    - **Transcript filters cannot fix wake-model false fires.** Same window, 2026-08-01 19:45: `hey_zeev` scored **0.96 on television audio** and the TV speech was transcribed and answered as a real question. That score sits *above* several genuine wakes (0.68, 0.92), so no threshold separates them — the levers are `OWW_ENERGY_MULT`, retraining, or accepting it. Measured rate over this window: **2 false in 5 triggers / ~27 h**.
    - **Porcupine was evaluated and rejected**: far cheaper at runtime (0.7% of a core, measured) but custom keywords are Enterprise-only at $6k/yr — the free tier is a 7-day trial pending review. Don't re-propose it.
  - **Cloud fallback**: used automatically when `OWW_MODEL_PATH` is unset or the model won't load. Records 2s chunks, applies an RMS gate then `_has_speech()`, and only then pays for Groq Whisper and substring-matches `_DEVICE_WAKE_WORDS`. **This bills per noisy 2s window, continuously** — it is a fallback, not a resting state.
  - **Behavior difference**: the cloud path can catch "Miss Minutes, what's the weather" in one window and pass the tail straight through; the local path fires on the phrase alone, so the follow-up is always recorded separately. Speak, pause, then ask.
  - **`_has_speech()`** (`zeev.py`, near `_rms`): webrtcvad at **aggressiveness 3, deliberately not the library default** — measured on this Pi, levels 0–2 passed every synthetic signal except digital silence (which the RMS gate already rejects), making the gate a no-op. Level 3 also rejects pure tones and hiss; broadband noise and mains hum still pass. Fails open when webrtcvad is missing so it can never make the device deaf. Pinned by `tests/test_wake_gate.py`. On Python 3.13 the Pi needs the **`webrtcvad-wheels`** fork — the original imports `pkg_resources`, dropped in setuptools 82.
- **Utterance recording: `max_seconds` is a CEILING, and the VAD that should end a turn early was dead for its whole life** (found live 2026-07-31). Two defects that only make sense together:
  - `record.Record` can only ever *shorten* a capture — there is no code path that lengthens one — so `max_seconds` was a hard wall and anything longer was cut mid-word. Three limits bound it and **must move together** or the smallest silently wins: `arecord -d`, `bufSize` (the `for n < bufSize` bound), and `deadline`. Enlarging one alone reproduces the bug with more allocation.
  - It also never shortened anything: `silenceThreshold` was a hardcoded **400** int16 RMS against a room floor of **~1300–1900** (the wake listener's own rolling median × `OWW_ENERGY_MULT`), so every frame read as speech, `speechEnd` was refreshed continuously, and the 1.5s silence rule could not fire. **Six hours of logs contained zero VAD stops**; a two-second question burned the full 8s. The tell is the wake→transcript gap being *identical* regardless of what was said.
  - **The daemon cannot measure the floor itself** — the mic opens only once the user is already mid-utterance, so its first frames are speech, not room tone. The wake listener is the only thing that hears the room while nothing is being said, so it publishes `_WAKE_NOISE_MED` and Python passes `silence_rms` on the `record` request. `sco_record` deliberately does **not** get it (8kHz call audio is a different signal with a different floor).
  - Ceiling is `ZEEV_RECORD_MAX` (20s). Raising it is only safe *because* VAD now ends turns — short questions finish faster than the old fixed 8s, not slower. A no-speech-in-4s guard stops a false wake from holding the mic for the whole ceiling.
  - **The failure modes are asymmetric and the code is biased accordingly**: too-low a threshold only costs latency (runs to the ceiling), too-high truncates the speaker. So the no-speech guard **distrusts the threshold, not the microphone** — if nothing cleared it but `peakRMS` shows real audio, it relaxes once to half the peak and keeps recording. The published median is volatile (3636 quiet, 6880 right after a restart with the greeting playing), which is exactly why that self-correction exists.
  - `record` logs start (`max`, `silence_rms`) and finish (duration, `peak_rms`, `speech`). Before that, a capture that ran to the ceiling logged *nothing* — the one measurement separating "never fired" from "fired too early" was the one missing.
- **A language *intent* gate swallowing a language *content* request** (live 2026-07-31): "Can you also say it in Hebrew?" matched `_LANG_SWITCH_RE` (`say` … `in Hebrew`), so Zeev answered "עובר לעברית" and never recited the prayer. Same failure class as the camera gates — a regex allowlist over unbounded phrasing eating the turn. An object between the verb and the language name (`_LANG_OBJECT_RE`: "it", "the prayer") now marks it content; "to me"/"to us" are indirect objects and must still switch.
  - **English is exempt on purpose.** `FORCED_LANG` is sticky, so reading "say it in English" as content would leave a user stuck in Hebrew with no spoken way back. Over-triggering toward English restores the default state; over-triggering the other way traps the device. The asymmetry is the point.
  - Falling through the gate is only half of it — `_HE_CONTENT_RE` was widened to `say|recite|read|translate|repeat|sing … in hebrew` so the turn reaches the LLM with the Hebrew-script instruction; `_speak_device` then picks Hebrew TTS off the script itself. **This is Hebrew-only** — an equivalent Spanish/Russian translation request falls through with no script instruction.
  - The trigger sat at the *end* of the utterance, so truncation was never involved even though the record cap was broken in the same turn. **Two unrelated bugs in one log line**; fixing the reported one would not have fixed the reported symptom. Pinned by `tests/test_intent_gates.py`.
- **Wake-word state coupling (bit us once)**: the listener only runs when `_face_state` is `idle`/`ready`. `_busy` is cleared *only* in `_go_idle()`, and the success path calls `_go_ready()` — so before this was fixed, one voice turn locked the wake word out for the rest of the boot. `_idle_sleep_watcher` now also drops a quiet `ready` session back to `idle`. The listener deliberately does **not** gate on `_screen_on[0]`.
- **429 fallback**: `_handle_transcript` retries 70B/GPT-OSS 429s with 8B before surfacing an error.
- **LLM error display**: Whisplay screen shows "Rate limited", "No network", or "LLM err <code>"; full detail in `data/zeev_errors.log`.
- **`_CAMERA_RE`**: natural-language camera intents → `capture_image()` + Llama 4 Scout vision call (when `CAMERA_AVAILABLE`).
- **`_VISUAL_TRIGGER_RE`**: visual-effect intents → runs the matching `shapes_test.py` effect (`fire`/`matrix`/`psychedelic`/`liquid`/`tunnel`/`plasma`/`cartoon`) on `board` for 12s; sets `_visual_effect_active[0] = True` first so `_face_loop` skips its own SPI writes (avoids two threads racing on `board.draw_image`).
- **`_push_lcd` / RGB565**: every frame is hand-converted to RGB565. This was a pure-Python loop over 240×280 = 67,200 pixels measuring **380 ms/frame on the Pi**, against a `_FACE_INTERVAL` asking for up to 8 fps (125 ms) — so the face loop could never hit its rate and simply pinned a core for the whole session. The numpy path (`_rgb565_np`) is **4.6 ms, an 83× speedup**; `_rgb565_py` remains as a fallback so a missing numpy degrades the frame rate instead of blanking the screen. Byte-equivalence is pinned by `tests/test_rgb565.py` — `>u2` (big-endian) byte order matters. If the display ever shows wrong colours or tearing, check that test first.
- Driver install: `cd ~/Whisplay && sudo bash install_driver.sh && sudo reboot`.
