# Wyze camera integration — full history

Extracted from CLAUDE.md 2026-08-06 (context-budget trim). This is the full
incident history behind Zeev's Wyze camera support; CLAUDE.md keeps only a
short current-state summary under "Wyze cameras" and points here. Read this
when actually working on camera code — nothing here is needed for unrelated
work.

House cameras reach the same vision path. Wyze exposes **nothing** on the LAN by itself — no RTSP, no snapshot endpoint, and the cloud API has no still-frame call — so `docker-wyze-bridge` runs on bosgame (`/opt/wyze-bridge`, `network_mode: host`, UFW-restricted to `10.0.0.0/24`) and republishes each camera as RTSP. `wyze_snapshot(stream)` pulls one frame with `ffmpeg -rtsp_transport tcp -frames:v 1` and hands the base64 JPEG to `vision_complete`.

- **Config**: `WYZE_RTSP_BASE` (`rtsp://user:pass@host:8554`), `WYZE_CAMERAS` (comma-separated stream names), `WYZE_SNAP_TIMEOUT`.
- **Streams authenticate with `WB_API`, not `WB_PASSWORD`** — separate credentials, and using the wrong one gives a bare 401. Now set via `STREAM_AUTH`, pinned to the Pi and bosgame IPs.
- **`_scrub_rtsp()` before logging anything from ffmpeg.** ffmpeg echoes the full input URL — password included — in *every* error line; that leaked a credential into a terminal transcript once. Pinned by `tests/test_wyze_cameras.py`.
- **`resolve_wyze_cam()` asks rather than guesses.** No match or an ambiguous match returns `None` plus the candidate list, and the turn replies "Which camera? I can check …". Describing the wrong room confidently is the same failure class as the wrong-city problem — the model states it as fact.
- `_WYZE_CAM_RE` is checked **before** `_CAMERA_RE` so naming a room looks at that room, not at whatever the Pi faces.
- **A missed camera gate does not fail safe — the 8B invents feeds.** Three turns on 2026-07-30 were answered with a fabricated report naming a "living room cam" and an "upstairs hallway cam" that do not exist, with the cat placed on a windowsill. The tell in the log is timing: `LLM done` in ~2.6s where a real vision turn is ~29s, and no `[wyze]` line at all. Three defects had to be fixed together, and the third is the one that generalises:
  - `_WYZE_CAM_RE` matched no plurals — `\bcam\b`/`\bcamera\b` both fail on "cameras", so "check all cameras" hit nothing.
  - "what do you see in the two cameras" hits `_CAMERA_RE` but resolves no room, so it reached *neither* camera branch (the Pi's own eye needs `CAMERA_AVAILABLE`, false on this board) and became ordinary chat. `_CAM_NOUN_RE` now routes it to the ask path — gated on `not CAMERA_AVAILABLE`, or an attached Pi camera would be pre-empted by "Which camera?".
  - **The gate is an allowlist over unbounded phrasing, so fallthrough is permanent by construction and needs its own guard.** `_build_system_prompt` now appends a `## Cameras:` block on any camera-shaped turn (incl. a bare `WYZE_SUBJECTS` name — "where is Smokey" matches no camera regex at all) stating that no image is present and naming the cameras that exist. Priming made it worse: the "Which camera? I can check bedroom cam, smokeys cam" reply stays in the session and the next turn read it as proof of access.
  - The guard names cameras via `wyze_cam_label()`, so it must never see `name=rtsp://…` entries — that would put stream URLs and LAN IPs into a prompt bound for Groq/OpenRouter. `WYZE_CAMERAS` holds bare names (URLs live in `WYZE_CAMERA_URLS`); pinned by `test_guard_never_leaks_stream_urls`.
  - **Hallucinated replies get embedded.** `message_vecs` had vectors for all three, so `retrieve_semantic` could surface them into a later prompt as fact. Cleaning up means deleting **both halves** of each turn — it pairs a user message with the *next* assistant row, so removing only the assistant re-pairs the user with a later reply.
  - **A genuine (non-hallucinated) vision reply still isn't a standing fact** (2026-08-04, `docs/research-directions.md` #2): `finish_turn(..., vision=True)` — and the two vision call sites outside `finish_turn` (web `/snap`, terminal `/look`) — prefix the **DB-stored** copy with `_VISION_TAG`. Only the stored copy; what's spoken and what's in `ctx.session` stay untagged, so nothing about this turn changes. When `_build_system_prompt` later surfaces that row via RAG, it strips the tag and appends a staleness caveat instead of letting the model treat "there's a cat on the couch" as still true. Applied at all 4 device-mode `finish_turn` vision-success sites (only when a frame was actually inspected, not on "couldn't get a picture") plus `/snap` and `/look`. **Live-measured limitation**: retrieval anchors on the embedding of the *user's trigger phrase* ("check the basement cam"), not the description itself, since `message_vecs` is keyed by user-role rows — "what did you see in the basement earlier" scored 0.72 and surfaced the hit, "is the cat still on the couch" scored 0.48 and didn't clear `min_sim`. Pinned by `tests/test_vision_grounding.py`.
- **A camera noun alone routes to the camera branch** (`_CAM_NOUN_RE`, when no Pi camera is attached and `_TOOL_INTENT_RE` doesn't match). Whisper mangles the *trigger*, not the noun: live 2026-07-30 it heard "check all cameras" as **"checko cameras"**, no verb survived any gate, and the 8B answered by repeating the *previous* turn's genuine camera description as a current observation — accurate enough to pass for working, which is what makes it worse than an obvious fabrication. The tool exclusion is why "remind me to buy a camera" is still a reminder.
- **Vision replies are stored stripped.** `_strip_stage_directions(reply)` was computed and thrown away in the single-camera branch — used only as an emptiness test — so a *partial* stage direction survived into `finish_turn`: live row 1906 reads `(Sarina's voice, composed and professional): I see a bedroom…`. Stored text feeds both the session and RAG, so that is what the next turn read back as observation. The sweep branch already kept the stripped value; the two now agree.
- **"check all cameras" sweeps** (`_ALL_CAMS_RE` → `resolve_wyze_sweep()`), because `resolve_wyze_cam()` returns a single stream and cannot express it — widening the regex alone only got the phrase as far as the "Which camera?" ask. Naming a room still wins: "check all the cameras in the basement" is a question about the basement. The quantifier must sit against the camera noun; a bare "all"/"both" is far too common in speech. Capped at `ZEEV_SWEEP_MAX_CAMS` (3), and the pool is `sweepable_cams()` — cameras with a direct RTSP URL, shared with the subject sweep, since the six bridge-only cameras each burn `WYZE_SNAP_TIMEOUT` before answering.
  - Same grab/vision overlap as the subject sweep (~50s for two cameras rather than ~58s), and the per-camera prompt demands **one or two sentences** — a sweep speaks every camera's answer in one reply, so unbounded descriptions become a minute of talking.
  - A camera that returns no frame is **named in the reply**. Silently dropping it reads as a full report of the house, which is the same overclaiming this whole section exists to prevent.
- **Latency is bad and it is announced**: ~50s end to end (keyframe wait + free-tier vision), so the branch speaks "Let me look at the …" first, like `youtube_play`'s "Looking for X". Note the 17s grab in testing was inflated by the synthetic stream's 250-frame GOP; real cameras key far more often.
- **Four of the eight cameras can never do RTSP** — `WVOD1` (Backyard, Front Yard), `ME_WCO3` (secret) and `HL_DB2` (Doorbell) have no RTSP image; **`secret` is a Wyze Solar Cam Pan under the June 2026 CPSC fire recall** (`WYZESCPWH`, 321k units, punctured battery from the wrong solar-panel screw) and is unsupported by the bridge regardless — it fails `IOTC_ER_UNLICENSE (-10)`, not the usual DTLS timeout. **Living Room, Backyard, Front Yard, and Secret are reachable via the phone-relay snapshot path** (`_PHONE_CAMERA_ALIASES` → `phone_camera_snapshot_remote()` → `DOG_CALLER_URL/snapshot`): the same Android phone that runs the dog-caller automation navigates to the camera's live view in the Wyze app and screenshots it. Latency is ~30s and announced. `"secret"` alone is deliberately not a matched alias — it's an ordinary English word, so the match requires `"secret cam"`/`"secret camera"`. Leo's room (`WYZEC1-JZ`, v2) and Living Room (`WYZECP1_JEF`, Pan v1) were the two RTSP-flashing candidates and **both bricked on the correct image and were recovered to stock** — Wyze's own forum states "some iterations of the V2 lost RTSP compatibility", and `4.28.4.49`/`4.29.4.49` are already the improved-compatibility final builds. **Do not retry; the ceiling is the two v3s.** See `docs/wyze-rtsp-flashing.md` for what that rules out. Model codes come free from the bridge's own `[+] Adding <name> [<model>]` log lines. **v2/Pan use `/live`, v3 uses `/stream0`.**
- **The bridge is blocked on hardware, not code**: cameras report `dtls: 1` and the bridge times out on the TUTK handshake (`IOTC_ER_TIMEOUT`) — a known open upstream issue. Confirmed on Leo's room too, so the bridge is a dead end for all six un-flashed cameras — flashing is the only route that works, and only two of them can take it.

**`upstairs` runs Wyze's RTSP firmware instead, and works** (2026-07-30). That bypasses the bridge and DTLS entirely: `WYZE_CAMERAS=upstairs=rtsp://10.0.0.217:554/stream0`, credentials in `WYZE_RTSP_USER`/`WYZE_RTSP_PASS`. Measured end to end: **grab 4.3s, vision 24.6s, 28.9s total**, 238 KB 1080p frame, correct description of the room.

**`basement-cam` flashed too** (2026-07-30, `10.0.0.84`), same `/stream0` path. End to end: **grab 7.7s, vision 21.0s, 28.7s total**. Both cameras share one login, so `WYZE_RTSP_USER`/`WYZE_RTSP_PASS` still covers them — but credentials are now resolvable **per camera** via `WYZE_RTSP_USER_<NAME>`/`WYZE_RTSP_PASS_<NAME>` (`wyze_credentials()`; `basement-cam` → `BASEMENT_CAM`), because each camera's login is typed into the phone app separately and a mismatch is a bare 401 with nothing pointing at the cause. A per-camera *user* with no per-camera password deliberately does **not** fall back to the shared password — sending the wrong secret to the wrong camera is worse than failing.

**Both flashed cameras were repositioned upstairs and renamed 2026-07-30**: `10.0.0.217` (was `upstairs`) → **`smokeys-cam`**, `10.0.0.84` (was `basement-cam`) → **`bedroom-cam`**. The flashing history below still says "upstairs"/"basement-cam" because that is what was flashed; the live names are in the Pi's `.env` (`WYZE_CAMERAS`). They share the credential pair, so the rename touched nothing else — a per-camera `WYZE_RTSP_USER_<NAME>` *would* have needed renaming with them, and a missed one is a bare 401. "check upstairs" and "check the basement" now match no camera and hit the "Which camera?" ask path, which is the intended outcome: no camera should answer for a room it no longer sees.

- **Grab time is not the cost**: both cameras return a frame in under 8s; the ~29s is almost entirely the free-tier vision model.
- The basement frame is what caught the **markdown-bold speaker label** bug: the model replied `**Sarina:** …`, `_STAGE_LABEL_RE` only matched a bare `Sarina:`, and `*` isn't stripped until *after* the label pass — so it was spoken as "Sarina colon". Fixed; pinned by `tests/test_stage_directions.py`.

- **The path is `/stream0`, not `/live`.** `/live` is the v2/Pan path and it cost real debugging time: the v3 firmware answers a raw `DESCRIBE /live` with `401 Digest` (so it *looks* like an auth problem) but ffmpeg reports only `Invalid data found when processing input` with no RTSP dialogue at all. Every credential theory was a dead end — a bare URL with no credentials gave the same error, which is the tell. `/stream0` is 1920×1080, `/stream1` is a 640×360 substream.
- **Flashing bricked the camera on the first attempt** — red LED, IR-cut click, power off, repeating, surviving both an SD-card removal and a PSU swap. Recovered by flashing *stock* firmware (`demo_wcv3.bin` at the root of a FAT32 card, hold setup while powering on, 3–6s, solid purple ≈5 min). Budget for that: the RTSP image is a pulled beta and both its CRCs validated, so a clean image is no guarantee of a clean boot.
- **Secure RTSP (RTSPS, port 322) does not work with ffmpeg** — TLS 1.3 self-signed, and ffmpeg fails the handshake with `Error in the pull function` with or without verification. Turn it off; port 322 keeps listening afterwards but stops answering TLS.
- **Never put a camera password in a URL or a shell command.** This one contained `%`, which `printf` ate — the value reached `.env` as 32 spaces plus `0.000000rak4^^+nop3=` — and its `@` then split the URL at the wrong place. `WYZE_RTSP_USER`/`WYZE_RTSP_PASS` are plain values, percent-encoded by `wyze_stream_url()`. Edit them with an editor, never `printf`.
