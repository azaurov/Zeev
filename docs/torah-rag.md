# Torah RAG (Sefaria) — full history

Extracted from CLAUDE.md 2026-08-06 (context-budget trim). CLAUDE.md keeps a
short current-state summary under "Torah RAG (Sefaria)" and points here.

FTS5 DB: `data/torah.db`. Sources: Tanakh, Mishna, Talmud, Apocrypha, Siddur/Haggadah, Zohar, Dead Sea Scrolls, Sumerian. Populated by `zeev/import_sefaria.py` (resume-safe, ~75 min full corpus).

- `needs_torah(text)` / `_TORAH_RE` — matches Torah, Talmud, Gemara, halacha, Apocrypha, liturgy, Zohar, DSS/Qumran, Sumerian, parsha/portion. `torah_search(query, k=3)` — FTS5 search; noise verbs/time words excluded to avoid polluting matching.
- DB schema: `passages` FTS5 table (`source`, `ref`, `en`, `he`); `done` tracks imported refs. Torah/Sefaria replies force `lang='he'` for TTS regardless of reply script.
- **Getting a named prayer to actually reach the model took FOUR independent fixes, and any one of them alone looks like the others didn't work.** All found 2026-07-31 from a single request for "the bedtime angelic prayer":
  1. **The gate** didn't match the phrase, so the turn never touched the DB (`_ANGEL_PRAYER_RE`).
  2. **`ref` is UNINDEXED**, so the passage was unfindable by name (`_torah_ref_lookup`).
  3. **`import_sefaria.py` truncated every passage at 4000 chars**, so the text did not exist locally.
  4. **`_build_system_prompt` sliced each hit to `en[:500]`**, so even the full text wouldn't have reached the model.
  - Numbers that make it concrete: the service is **10678 chars** and its angels invocation sits at **offset 9238 (87% in)**. The 4000 cap severed it; a 500-char head slice misses it by 8700 chars.
  - **Re-import is NOT a re-run.** The `done` table makes the importer resume-safe, so a plain re-run skips every ref and the new cap has no effect. Both tables must be cleared. Ran on bosgame (8 cores, 14GB) rather than the Pi — 75 min with 3 workers, and the Pi had 181 MB free with zeev-device using 281.
  - Cap raised 4000 → **`MAX_PASSAGE_CHARS = 20000`**, covering all four sites (`en`+`he` in the main path, plus DSS and Sumerian). Result: **20832 rows, identical per-source counts to before (nothing lost)**, 6319 rows now longer than the old cap, DB 110.7 → 148.9 MB. **34 rows still hit 20000** (24 Zohar, 16 Sumerian, 2 Siddur, 1 Gemara) — 0.16%, down from 30%.
  - **Failure counts are not regressions**: Gemara 65 failed / 5349 inserted, liturgy 16 / 508, Zohar 1 / 1806 — every inserted count matches the old DB exactly, so those refs simply have no content on Sefaria.
- **`torah_excerpt()` centres the window on what was asked, not the passage's opening.** Query words first, then the alias's **focus terms** — necessary because what people say is routinely absent from the translation ("bedtime" and "angelic" appear nowhere in this passage's English). Focus is a fallback, never an override, or asking about the forgiveness section gets dragged to the angels. Budget is shared (`2400 // n`, floor 600) so a single exact alias hit gets room while three loose FTS hits stay terse. The window is **ellipsis-marked** so a mid-passage excerpt isn't read as the opening.
- **`torah_search` returns `(ref, en, he)` — arity changed from 2.** For most siddur rows the Hebrew lives *only* in `he`, so "say it in Hebrew" reached the model with English text alone and it **invented the Hebrew** — the original bug, still live after fixes 1–4. The Shabbat Amidah rows hide this: Sefaria has no English for them, so their `en` already holds Hebrew. The Hebrew is attached only when the turn asks for it (tokens).
  - **`torah_excerpt_he()` projects the window from the English match** — the query is English, the text is pointed Hebrew, so keyword search cannot locate it. `en` and `he` are parallel renderings, so the *fraction* transfers: angels at 9238/10678 English (86.5%) and 7614/8813 Hebrew (86.4%), landing within ~10 chars.
- **`ref` is `UNINDEXED` in the FTS5 schema — only `en` is searchable.** So a passage whose *title* never appears inside its own English translation cannot be found by `MATCH` however it is spelled, and that is most of the siddur: Shalom Aleichem, Ma Tovu and Asher Yatzar were all present and all unreachable. Found 2026-07-31 when "help me with the angelic prayer" reached the 8B unsourced and it invented both an English text and a Hebrew one, naming a prayer (*"Tefillat HaShalom"*) that does not exist — while **Shalom Aleichem, the Friday-night hymn addressed to the ministering angels, was in the DB the whole time**.
  - `_torah_ref_lookup()` probes `ref` with `LIKE` and its hits **lead** the results: naming a prayer is a far stronger signal than an OR over its words, which just retrieves whatever shares vocabulary.
  - **Bigrams first, long single words second.** Prayer names are overwhelmingly two words, and a single one drags in whole sections (`shabbat` alone matches 205 rows). The tokenizer takes **2-char** words specifically because "Ma Tovu" needs `ma` to form its bigram at all — at a 3-char floor one word remains, no bigram forms, and the lookup silently returns nothing. `_TORAH_REF_SKIP` absorbs the function words that admits, plus generic corpus words (`prayer`, `blessing`, `hebrew`) that would otherwise crowd out the real hit.
  - **Each `LIKE '%x%'` is a full scan of ~20k rows.** Eight separate probes measured **923ms** on the Pi Zero; one OR'd query per tier brings it to **260–780ms**, against a Torah turn that already runs ~30s. Don't reintroduce per-candidate queries.
  - Coverage is **Shabbat 205 / Weekday 172 / Festivals 59** — an earlier commit message claiming "weekday only" was wrong, and the difference matters: absent-from-DB and present-but-unsearchable need opposite fixes. Genuinely absent: Shehecheyanu, Lecha Dodi, Kol Nidre, Hashkiveinu, Elohai Netzor. Those need `import_sefaria.py`, not a search change.
  - Pinned by `tests/test_torah_ref_lookup.py`, whose fixture **mirrors `UNINDEXED` deliberately** — a test built on an indexed `ref` passes without the fix.
- **`_ANGEL_PRAYER_RE` is separate from `_TORAH_RE` because a flat alternation cannot express proximity.** Bare "angelic" is ordinary English ("she has an angelic voice"), so it needs a prayer word within 30 chars. "The angelic prayer" is not a standard liturgical name — it is what Alex calls it, and Whisper spells names however it hears them.
- **`torah.db` has chapter granularity only** — one row per chapter, verses joined by spaces with no markers, so text *cannot* be trimmed to a verse. That matters because a parsha routinely starts mid-chapter: Eikev is `Deuteronomy 7:12-11:25`. `_parse_torah_ref` used to discard the verse numbers and `get_parsha_text` handed over whole chapters under a header naming the exact reference, while the prompt said "read the text above from the beginning" — so asking for Eikev opened at Deut 7:1, **eleven verses inside Va'etchanan**, labelled as Eikev. `_parse_torah_ref` now returns `(book, chapters, first_verse, last_verse)` (arity changed from 2), each chapter is bracketed with its number, and the first/last carry the portion's real bounds. The boundary is *stated*, not trimmed — a verse-accurate fix needs verse-level rows from `import_sefaria.py`, which is the real remedy if this matters more later. Pinned by `tests/test_parsha_reference.py`.
- **A fifth call site missed the model/token override** (found in an autonomous test-and-fix pass, 2026-08-04): the terminal main loop, web `/chat`, and device mode all force `MODELS["2"]` (70B) and a token cap ≥1200 when `needs_torah`/`needs_parsha_reading` matches, because 8B's 6k TPM limit can't carry a full Torah passage. Both `/thermal` handlers (web SSE and terminal) build a Torah-checkable `ctx` string (`f"[thermal camera] Min {min}°C, ... {question}"`) but never checked it — a thermal question that also touches Torah content ("warm enough in here for shabbat?") stayed on 8B with `max_tokens=600` regardless. Both now check `ctx`, not just `question`, before picking the model/cap — same pattern as the other three sites, just reachable from a fourth path that got missed when it was added. Pinned by `tests/test_thermal_torah_routing.py` (the detection gate only; neither `/thermal` handler has an integration harness).
